### 2. ✅ Fixed Webhook Delivery — Shutdown Hook Pattern

**Problem:** `wp_remote_post` with `blocking: false` silently drops requests on PHP-FPM (Combell/Plesk).
WordPress sets `CURLOPT_TIMEOUT = 0.01s` (10ms) in non-blocking mode. A Cloudflare TLS handshake
takes 20–80ms, so the connection is killed before the request is sent. WordPress returns no error.

**Diagnosis:**
- Blocking WP-CLI test: returned HTTP 200, product appeared in KV ✅
- Non-blocking WP-CLI test: returned no error but product NOT in KV ✗
- This confirmed it was not a credentials/routing issue but a transport issue

**Fix applied to both PHP files:**
```php
private function send_webhook($endpoint, $data) {
    $url       = $this->get_webhook_url() . $endpoint;
    $payload   = json_encode($data);
    $signature = base64_encode(hash_hmac('sha256', $payload, $this->webhook_secret, true));

    add_action('shutdown', function() use ($url, $payload, $signature) {
        // Flush and close browser connection first (PHP-FPM only)
        if (function_exists('fastcgi_finish_request')) {
            fastcgi_finish_request();
        }
        wp_remote_post($url, array(
            'timeout'  => 10,
            'blocking' => true,
            'headers'  => array(
                'Content-Type'           => 'application/json',
                'X-WC-Webhook-Signature' => $signature,
            ),
            'body' => $payload,
        ));
    });
}
```

**Result:** `fastcgi_finish_request()` closes the browser connection before the cURL call,
so `blocking: true` with a 10s timeout doesn't delay the admin page response.

### 4. ✅ Fixed KV Write Limit Exhaustion (forceRefresh: false)

**Problem:** After a few product saves the worker stopped updating KV and never triggered rebuilds.
Worker returned HTTP 200 to each webhook but background `ctx.waitUntil()` tasks were silently failing.

**Diagnosis:** `POST /trigger-rebuild` returned `"KV put() limit exceeded for the day."`

**Root cause:** `syncSingleProduct` called `syncImageToKV(..., forceRefresh: true)` on every
webhook-triggered save. With 5 images × 2 sizes (full + thumb) + 2 product KV writes + 1 index
write = ~13–19 writes per save. Cloudflare free/standard plan: **1,000 writes/day**.
A few saves exhausted the daily limit.

**Fix — `workers/product-sync/src/index.ts`:**
```typescript
// Before (all 4 syncImageToKV calls in syncSingleProduct):
let mainSuccess = await syncImageToKV(env.PRODUCTS_KV, mainUrl, product.slug, i, true, 'full');

// After:
let mainSuccess = await syncImageToKV(env.PRODUCTS_KV, mainUrl, product.slug, i, false, 'full');
```

`forceRefresh: false` means images are only written to KV when not already cached.
A typical title/price/text edit now costs 3–4 KV writes instead of 13–19.
Images are re-cached only when the WordPress filename changes (new image upload).

### 8. ✅ Applied product:index Zero + Threshold Guards

**Problem:** If WooCommerce API returns an empty or very small response (timeout, error),
`syncAllProducts` would overwrite the full product index with an empty/partial list,
breaking all category pages.

**Fix — `workers/product-sync/src/index.ts`:**

Added `forceIndex: boolean = false` parameter to `syncAllProducts`. Guards added before writing `product:index`:

```typescript
const existingIndexStr = await env.PRODUCTS_KV.get('product:index');
const existingCount = existingIndexStr ? JSON.parse(existingIndexStr).length : 0;
const threshold = Math.floor(existingCount * 0.8);

if (allProducts.length === 0) {
  console.error(`syncAllProducts: WooCommerce returned 0 products — skipping product:index write`);
} else if (existingCount > 0 && allProducts.length < threshold && !forceIndex) {
  console.error(`syncAllProducts: WooCommerce returned ${allProducts.length} products but existing index has ${existingCount} (threshold: ${threshold}) — skipping. Add ?force_index=true to /sync to override.`);
} else {
  // Safe to write
  await env.PRODUCTS_KV.put('product:index', JSON.stringify(productIndex));
}
```

`/sync` endpoint now reads `?force_index=true` to bypass the threshold guard when intentionally removing products.

## Key Learnings

### wp_remote_post blocking:false Fails on PHP-FPM
WordPress non-blocking mode sets `CURLOPT_TIMEOUT = 0.01s` (10ms). A Cloudflare TLS handshake
takes 20–80ms. The TCP connection is killed silently with no PHP error or log entry.
**Always use the shutdown hook pattern for webhook delivery on PHP-FPM hosts.**

### Cloudflare KV Write Limit
Free/standard plan: **1,000 writes/day**. `ctx.waitUntil()` failures are silent — the worker
returns HTTP 200 to the caller. Diagnose by calling `/trigger-rebuild` directly; if KV limit is
hit it returns an error message. `forceRefresh: true` on images costs ~10–16 extra writes per
product save. Use `forceRefresh: false` in single-product webhook syncs.

### product:index Safety Guards
Always guard the `product:index` write with:
1. Zero check (never write if WooCommerce returned 0 products)
2. 80% threshold check (never write if result is <80% of existing count, unless force override)

### PHP Binary on Combell (Plesk)
`php` is not in PATH. Use `/opt/plesk/php/8.3/bin/php` explicitly for syntax checks and WP-CLI.
